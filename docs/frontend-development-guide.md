# Guía de desarrollo del frontend — ColivinApp

> **Documento derivado.** La fuente de verdad funcional es `docs/` (SRS v3 + diagramas); los contratos reales viven en `api/`. Si algo aquí contradice esas fuentes, prevalece la fuente original y esta guía se corrige. El estado operativo del momento está en `memory-bank/` (raíz del repositorio). Documentos complementarios: `docs/backend-debt-backlog.md` (deuda y defectos del backend, con reproducción) y `docs/requirements-status.md` (matriz RF: frontend / backend / end-to-end).

## 1. Alcance y estado

- Frontend web en `client/`: Angular 22.2.1 (standalone, zoneless), TypeScript 6, Tailwind CSS 4.3 (CSS-first), Vitest 5. Scaffold SSR presente; política de renderizado por ruta decidida y documentada en ADR-004 (§10).
- Backend: monolito modular Kotlin/Spring en `api/`; API REST en `/api/v1`; token opaco `Bearer`; sin CORS.
- Estado actual: **M0–M6 completados** (M4 reservas + mensajería; M5 comunidad + reputación; M6 administración), todos **validados contra el backend real**. M6 añade el área interna para moderadores/administradores: cola de casos con trazabilidad (RF-082), revisión de documentos con motivo obligatorio (RF-080), revisión de publicaciones (RF-081), catálogos (RF-083), indicadores reales de la cola (RF-084, alcance parcial) y reglas de beneficio (RF-073). **Matices registrados**: (a) el frontend de M4-B está verde, pero **RF-052 «bloqueo» no está verde end-to-end** (`POST /users/me/blocks` ⇒ 500); (b) **RF-072 «disputa» no es ejecutable** (`POST /reviews/{id}/dispute` ⇒ 400 siempre); (c) **RF-083 «catálogos» no es ejecutable**: el alta responde 400 con `parentId` nulo (incluso en categorías planas) y 404 si se envía uno, porque no puede existir la primera entrada; (d) revisar un recurso fuera de su estado de revisión devuelve **409 `CONFLICT`** desde F0 (antes 500 con traza: ver `docs/architecture/ADR-008-superficie-error-api.md`). En todos los casos la UI ofrece la funcionalidad, muestra el error real del servidor y **no** compensa el defecto desde Angular. **RF-085 (auditoría) no tiene contrato**: lo único expuesto es la trazabilidad `events[]` de cada caso. M6 no arranca M7: no hay siguiente milestone definido.

## 2. Arquitectura y estructura

Estructura **feature-first** alineada a los bounded contexts del backend (ADR-002):

```text
client/src/app/
├── core/        # transversal real: sesión/auth, HTTP (interceptores, errores), configuración de API
├── layout/      # shells visuales: público, autenticado, administración
├── shared/      # UI y utilidades sin dominio (solo con ≥2 consumidores reales)
└── features/
    ├── marketing/  # landing y páginas públicas estáticas (sin API)
    ├── auth/       # registro, verificación de correo, login, logout, reset
    ├── profile/    # perfil, privacidad, consentimientos, verificación documental
    ├── listings/   # búsqueda, detalle de publicación, disponibilidad, favoritos
    ├── directory/  # directorio público de ciudades y universidades (API-Colombia)
    ├── host/       # propiedades, unidades, publicaciones, precio/reglas, bloqueos
    ├── bookings/   # reservas: vistas huésped y anfitrión
    ├── messaging/  # conversaciones, mensajes, notificaciones, bloqueos/reportes
    ├── community/  # actividades: vistas anfitrión y residente
    ├── reviews/    # evaluaciones, score y factores, disputas, beneficios
    └── admin/      # verificación, moderación de publicaciones, casos, catálogos, métricas
```

Reglas de dependencia:

- `features → core/shared/layout`; nunca al revés.
- Prohibido importar internals de otra feature (`features/a → features/b/...`).
- `shared`: solo código sin dominio con ≥2 consumidores reales. `core`: solo transversal real.
- Estado: local → feature → transversal; sin librería global de estado (ver §7).

Mapeo con el backend (cada feature consume su contexto real): `auth`→identity(auth) · `profile`→profile+identity(me) · `listings`→search+accommodation(público) · `directory`→API-Colombia(catálogo público externo: ciudades + universidades) · `host`→accommodation(host) · `bookings`→booking · `messaging`→messaging · `community`→community · `reviews`→reputation · `admin`→moderation+catalog+identity(admin)+accommodation(admin).

## 3. Estructura interna de una feature

```text
features/<dominio>/
├── pages/        # componentes de ruta (una página por ruta)
├── data-access/  # servicios HTTP del dominio + mapeo de errores
├── models/       # interfaces/uniones que reflejan los DTOs reales del API
├── state/        # estado de feature compartido entre sus páginas (p. ej. favoritos), provisto por ruta
└── ui/           # componentes internos de la feature (no compartidos)
```

## 4. Convenciones

- **Idioma**: identificadores de código en inglés; textos de UI y documentación en español.
- **Nombres**: ficheros kebab-case sin sufijo de tipo (estilo Angular v20+): `login-page.ts` (`LoginPage`), `auth-session.ts` (`AuthSession`).
- **Formato**: Prettier (`client/.prettierrc`, printWidth 100, singleQuote). Sin ESLint configurado (decisión M0, ver §15).
- Componentes: uno por fichero; templates inline solo si son pequeños; páginas con template externo.
- Prohibido `ngClass`/`ngStyle`; `class`/`style` bindings. Control flow nativo (`@if`, `@for` con `track`).
- Sin `any`; sin `!` injustificado; enums del backend como union types.

## 5. Integración con la API

- **Base URL**: relativa `/api/v1`. En desarrollo el dev-server proxya `/api` → `http://localhost:8080` (`client/proxy.conf.json`). En producción se asume **same-origin** (ADR-001). El backend **no tiene CORS**: nunca llamar a `:8080` directo desde el navegador.
- **Autenticación**: `POST /api/v1/auth/login` devuelve `{ token, expiresAt, user }`; el token (opaco, TTL 30 días) viaja como `Authorization: Bearer <token>`. `POST /auth/logout` lo revoca. El 401/403 del filtro de seguridad puede traer solo `{ "message": "..." }`.
- **Errores**: `ErrorResponse { code, message, fieldErrors? }` (`api/.../shared/presentation/dto/ErrorResponse.kt`). `fieldErrors` → validación de formularios; `code` → decisiones de UI.
- **Gates de negocio** (aplicados por el backend; la UI los comunica): verificación `COMPLETO` para publicar (anfitrión) y para crear solicitud (huésped); solo publicaciones `PUBLICADA` reciben solicitudes (RN-03); snapshot económico inmutable (RN-07).
- **Enums relevantes** (Kotlin → union type): `RoleCode`, `ConsentType`, `CatalogCategory`, estados de publicación/reserva/documento (consultar `domain/enums` de cada contexto antes de tipar).
- **Subida de archivos**: multipart; límite del servicio 10MB. Validar tipo/tamaño en cliente y mostrar errores del backend.
- **Verificación de correo / reset (dev)**: el backend solo registra el token en logs (`LoggingEmailSender`); la UI acepta token manual y por `?token=` en la URL.
- **Ciclo de sesión real (M1)**: el login exige correo verificado (`status ACTIVE`); el token es opaco (solo su hash se persiste en el servidor), TTL fijo de 30 días y **sin renovación**; `POST /auth/logout` revoca el token del dispositivo (idempotente). La sesión se persiste en `localStorage` (`AuthSession`, ADR-003) y se sincroniza con `GET /users/me` al arrancar.
- **Perfil con semántica de reemplazo**: aunque `PATCH /api/v1/profile` documenta actualización parcial, `Profile.update` sobrescribe todos los campos → el formulario envía el perfil completo leído con `GET /profile` (ciudad y datos académicos sin UI se conservan). `PUT /profile/privacy` recibe ambos booleanos.
- **Consentimientos**: `PUT /users/me/consents/{type}` exige `version` + `purpose`; el backend solo los almacena, así que los aporta el frontend (`features/profile/models/consent-documents.ts`) hasta que existan documentos legales versionados.
- **Verificación documental**: `POST /users/me/verification-documents` es multipart (`type` + `file`), admite JPG/PNG/WEBP/PDF y limita a 10 MB (validado también en cliente); el nivel «COMPLETO» deriva de tener ≥1 documento aprobado.
- **Rol activo (RF-004)**: solo se pueden elegir `HUESPED_ESTUDIANTE`, `HUESPED_TURISTA` o `ANFITRION`; exige correo verificado y datos mínimos de perfil (huésped: nombre + tipo; anfitrión: nombre + teléfono). El `CONFLICT` del backend se comunica con mensaje y enlace a completar el perfil.
- **Búsqueda real (M2)**: `GET /search/listings` acepta `cityId`, `minPrice`/`maxPrice`/`currency`, `availableFrom`+`availableTo` (juntos, `to > from`, ≤366 noches), `sort` (`RECENT` por defecto, determinista) y filtros por catálogo (`services` como lista de UUID, `roomTypeCode`, `accessibilityCode`, `minNights`). Ciudad y filtros de catálogo **aún no se exponen en UI** (no hay endpoint público de catálogos); la landing envía texto de ciudad/universidad que la búsqueda muestra como limitación conocida.
- **Detalle (M2)**: `GET /publications/{id}` devuelve `PublicationDetailView` anidado (`publication`, `property`, `unit`, `pricing?`, `rules?`); las publicaciones **no gestionan fotografías** todavía (las tarjetas de la landing usan imágenes de ejemplo marcadas como tal).
- **Disponibilidad (M2)**: `GET /publications/{id}/availability?from&to` devuelve un ítem por día en el intervalo `[from, to)` con `state` (`DISPONIBLE`/`BLOQUEADO`/`OCUPADO`) y `reserved`; los bloqueos del anfitrión llegan como `BLOQUEADO`.
- **Favoritos (M2)**: `GET/POST/DELETE /favorites[/{publicationId}]`; `POST` devuelve 201 (solo PUBLICADA) y un duplicado responde `CONFLICT` (se trata como «ya guardado»); `DELETE` de un no-favorito responde `NOT_FOUND` (se trata como «ya quitado»).
- **Área de anfitrión (M3)**: todo bajo `/api/v1/host/**` y con rol activo `ANFITRION`. Propiedades: `GET/POST /host/properties`, `PATCH /host/properties/{id}` (reemplazo de campos, ver §15). Unidades: `GET/POST /host/properties/{id}/units`, `PATCH /host/units/{id}` (los `null` explícitos conservan `typeCode`/`accessibilityCodes`, sin catálogo público que los alimente). Publicación (1:1 con la unidad): `POST /host/units/{id}/publication` (nace en `BORRADOR`) y transiciones `POST /host/publications/{id}/{publish|pause|hide|request-review|archive}`; **no existe endpoint de lectura** de publicaciones del anfitrión (ADR-005). Economía y reglas: `PUT /host/publications/{id}/pricing` y `PUT /host/publications/{id}/rules` (reemplazan el recurso completo). Bloqueos: `PUT`/`DELETE /host/units/{id}/availability/blocks?from&to` con intervalo `[from, to)` que devuelve la disponibilidad resultante día a día.
- **Gate de publicación (M3)**: publicar exige verificación `COMPLETO` del anfitrión; el `CONFLICT` del backend se comunica con mensaje explícito y enlace a `/perfil/verificacion` (no se trata como error técnico).
- **Reservas — huésped (M4, `/api/v1/reservations`, roles activos `HUESPED*`)**: `POST /` (201 · `{unitId, fromDate, toDate, occupants, message?}`), `GET /mine` (orden `createdAt` desc), `POST /{id}/confirm` y `POST /{id}/cancel` con `{reason}` **obligatorio**. La reserva devuelve el **snapshot económico** (`pricePerNight`, `currency`, `cancellationPolicy`, `totalPrice`) y `holdExpiresAt`; no hay `GET /{id}` ni historial para el huésped.
- **Reservas — anfitrión (M4, `/api/v1/host/reservations`, rol activo `ANFITRION`)**: `GET /` (recibidas), `GET /{id}/history` (historial **solo en esta ruta**), `POST /{id}/accept|reject|request-info` (`{reason?}`) y `POST /{id}/cancel` (`{reason}`). Decidir exige ser el dueño de la unidad; aceptar bloquea el rango y abre el hold.
- **Estados y transiciones (M4)**: `SOLICITADA · INFORMACION_SOLICITADA · ACEPTADA · CONFIRMADA · RECHAZADA · CANCELADA · EXPIRADA`. `accept`/`reject` desde `SOLICITADA` o `INFORMACION_SOLICITADA`; `request-info` solo desde `SOLICITADA`; `confirm` solo desde `ACEPTADA` y dentro del hold; `cancel` desde los cuatro estados vivos; `EXPIRADA` es del sistema. Cada transición registra un evento (`CREADA`, `ACEPTADA`, …) con actor, motivo y momento.
- **Mensajería (M4-B)**: `GET /conversations` (hilos del usuario, más recientes primero), `POST /conversations` (idempotente; **corregido en F0**, ya no responde 500), `GET /conversations/{id}` (hilo + `stay{fromDate,toDate}` + todos los mensajes), `POST /conversations/{id}/messages` (`{body}` 1..2000, 201), `POST /reservations/{reservationId}/messages` (**crea el hilo** y escribe el primer mensaje; devuelve `conversationId`), `GET /notifications` (`unreadCount` + lista), `POST /notifications/{id}/read`, `POST /conversations/{id}/reports` (`{reason}` 1..1000 → 201 con `caseId`; segundo reporte 409), `GET /conversations/reports`, `POST /users/me/blocks` (**hoy responde 500**), `DELETE /users/me/blocks/{blockedUserId}` (204/404), `GET /users/me/blocks`.
- **Comunidad — reglas reales (M5)**: una actividad pertenece a **una propiedad** y nace con la **comunidad autorizada** (participantes habilitados) fijada al crearla; el residente solo ve actividades donde tiene fila de participante (si no, **403**). Estados almacenados mínimos: actividad `PROGRAMADA|CANCELADA`, participación `HABILITADO|CONFIRMADA|RETIRADA`; **«ya pasó» se deriva de `scheduledAt`** (no se almacena y no hay scheduler). Confirmar exige actividad abierta, cupo libre y no estar confirmado, y toma el cupo con `SELECT … FOR UPDATE` (**409** si se llenó, si está cancelada, si la fecha pasó o si ya estaba confirmada). Retirarse exige estar `CONFIRMADA`, **pero no exige actividad abierta** (verificado: 200 en una actividad cancelada) — la UI ofrece la acción y refleja el estado real. La **pertenencia** de los habilitados la valida el backend (**400** «Enabled participants must belong to the property's community»), así que la lista de residentes que muestra el formulario es una **proyección de lectura** derivada de `/host/properties` + `/host/properties/{id}/units` + `/host/reservations` (huéspedes con reserva `CONFIRMADA` sobre unidades de la propiedad), nunca una verdad de servidor.
- **Comunidad — resumen agregado (RF-062, M5)**: `GET /community/summary?propertyId` devuelve **solo contadores** (`residentCount`, `consentedResidentCount`, `upcomingActivityCount`) y un flag `available`; con `available=false` el backend no considera suficiente el consentimiento ⇒ **la UI no muestra ningún contador** (mensaje informativo). El consentimiento que lo decide es el de privacidad (`ConsentType.PRIVACIDAD`), que cada persona gestiona en su perfil.
- **Reputación — reglas reales (M5)**: `POST /reviews` evalúa **la contraparte** de una reserva `CONFIRMADA` (`relationType: ESTANCIA`, `relationId` = id de la reserva); el sujeto **no lo elige** el cliente y **solo hay una evaluación por autor y evento** (**409** «This relation was already evaluated»). Las **cinco categorías son obligatorias** 1..5 (**400** «Every category must be rated: missing […]») y el comentario es opcional (≤1000). Una evaluación `DISPUTADA` **deja de contar** para el score y `GET /users/{id}/reputation` **calcula y guarda una instantánea en cada lectura** (write-on-GET): la UI lee una vez por visita y solo recalcula con una acción explícita. El score trae `factors` (peso, valor normalizado, contribución), `formulaVersion` y los `benefits` vigentes **en solo lectura** (su administración es de M6/RF-073). **RF-072 (disputa) está roto en el backend** (§15).
- **Administración — accesos y reglas reales (M6)**: `/api/v1/admin/**` exige **rol activo** `MODERADOR` o `ADMINISTRADOR` (el backend no distingue entre ellos; el SRS nombra moderador, soporte y administrador, pero solo existen dos roles internos). Sin sesión ⇒ **401** `{message}`; con sesión sin rol interno ⇒ **403** `{message}` (sin `ErrorResponse`). La UI usa `roleGuard('MODERADOR','ADMINISTRADOR')` y oculta el enlace, porque las autoridades del backend salen del rol activo (`User.activeRoleCodes()`): un usuario con otro rol activo recibiría 403 aunque tuviera el rol interno asignado.
- **Administración — moderación (RF-082)**: `/admin/cases` con `type|status|priority|assigneeUserId|onlyOpen` (filtros server-side, **sin paginación ni orden**), `GET /{id}` con `events[]` (trazabilidad = única auditoría expuesta), `assign`/`review`/`resolve{resolution}`/`reject{reason}` (nota ≤1000). Los estados terminales (`RESUELTO`/`RECHAZADO`) rechazan toda acción con **409** «The case is already closed». `/admin/cases/metrics` es el único indicador real (RF-084 parcial: no hay usuarios/publicaciones/solicitudes/conversiones ni filtro de periodo).
- **Administración — documentos (RF-080)**: `GET /admin/verification-documents?status`, `approve` (204, sin motivo), `reject{reason}` y `request-correction{reason}` (motivo obligatorio ⇒ **400** si falta). Solo los documentos `PENDIENTE` se revisan: en otro estado el backend responde **409 `CONFLICT`** (desde F0; antes 500 con traza). `DocumentSummary` **no expone usuario ni archivo**: el moderador no puede ver a quién pertenece ni el contenido.
- **Administración — publicaciones (RF-081)**: `GET /admin/publications` (sin `status` ⇒ cola `EN_REVISION`) y `POST /{id}/review {decision, note}`; `note` obligatoria salvo `APROBADA` (si falta ⇒ **400**); solo desde `EN_REVISION` (fuera ⇒ **409**, desde F0). Resultados reales: `APROBADA` → `PUBLICADA`; `RECHAZADA` → `BORRADOR` si era borrador y `OCULTA` si estaba publicada; `CORRECCION_SOLICITADA` → siempre `BORRADOR`. `PublicationView` no trae anfitrión, propiedad ni fotografías.
- **Administración — catálogos (RF-083)**: `GET/POST /admin/catalogs/{category}`, `PUT /{category}/{id}` (nombre y descripción) y `DELETE /{category}/{id}` = **desactivar** (no hay endpoint de reactivación aunque el servicio `activate` exista). Jerarquía real `FACULTAD→INSTITUCION`, `CARRERA→FACULTAD`. **El alta está rota en el backend**: `parentId` es `@NotNull` ⇒ 400 en categorías planas y 404 si se envía un UUID inexistente, así que no puede crearse la primera entrada. La UI expone la capacidad, muestra el `fieldErrors` real y declara la limitación.
- **Administración — reglas de beneficio (RF-073)**: `POST /admin/benefit-rules` (código único ⇒ 409, `minScore` 0..5, código ≤60, descripción ≤200), `GET ?activeOnly` y `POST /{id}/deactivate`. Sin edición ni reactivación. El cálculo del score y la concesión siguen en el backend: la UI solo configura datos (verificado en E2E: crear una regla hace aparecer el beneficio en la reputación y desactivarla lo retira).
- **Administración — descubrimientos fuera del alcance de `docs`** (documentados, sin UI): `GET /admin/roles` y `POST /admin/users/{userId}/roles` (asignación de rol interno, no está en RF-080..085), categorías `TIPO_HABITACION`/`ACCESIBILIDAD`, y la reactivación de catálogo/reglas.
- **Búsqueda y presupuesto (auditoría post-M6)**: `GET /search/listings` compara `minPrice`/`maxPrice` contra **`pricePerNight`** (`SearchListingsService`): el contrato **no tiene presupuesto mensual**. El buscador de la portada expresa la intención del producto («máximo mensual», 300.000–5.000.000 COP por defecto «sin límite») y la página de búsqueda la traduce con `nightlyCapFromMonthlyBudget` (`features/listings/models/listings-models.ts`, **mes de referencia de 30 noches**) al tope por noche que sí se envía, añadiendo `currency=COP` porque los precios del piloto están en COP. La UI muestra **las dos cifras** (mensual y su equivalente por noche) para no comunicar un filtro distinto del aplicado, y un `maxPrice` explícito en la URL manda sobre la conversión. Con los datos sembrados (420.000–1.200.000 COP tratados como precio por noche) el tope mensual realista no encuentra resultados: es una discrepancia de datos/semántica registrada en `docs/backend-debt-backlog.md` (#13), no un fallo de la UI.
- **Reputación de terceros — decisión de alcance (M5)**: el endpoint de reputación es accesible para cualquier autenticado, pero el frontend **no amplía el alcance**: la reputación de un usuario solo se enlaza desde el contexto de reserva del anfitrión hacia el huésped (`/reputacion/usuario/:id`); no se enlaza la del anfitrión para el huésped ni se acopla `reputation` con `messaging` para resolver identificadores. Es una decisión de producto, no una limitación del backend.
- **Directorio externo de ciudades y universidades (API-Colombia)**: `features/directory` consume la API pública abierta **API-Colombia** (`https://api-colombia.com/api/v1`; CORS `*`, sin autenticación) para ofrecer `/directorio`: búsqueda de **ciudades** (`GET /City` + `GET /Department` para resolver el nombre del departamento) y de **universidades** (`GET /HigherEducationInstitution`). La API **no tiene endpoint de búsqueda por texto**: cada colección se descarga **una vez por sesión** (promesas memoizadas en `DirectoryApi`, siguiendo la recomendación de caché de la API y su límite de 60 req/min) y el filtrado/orden es **local** con funciones puras (`features/directory/models`: tolerante a tildes, prioriza coincidencias por inicio y acota a 40 resultados). Es un directorio **de consulta**: sus identificadores son enteros de API-Colombia y **no** son los UUID de los catálogos del backend, así que **no** se envía como filtro de `GET /search/listings` — la limitación del filtro por ciudad/universidad se mantiene y se declara en la UI de búsqueda, que enlaza al directorio. El `authInterceptor` adjunta el token `Bearer` **solo** a las rutas del backend propio (`/api/...`): las llamadas a terceros nunca reciben la credencial de ColivinApp y un `401` externo no cierra la sesión.

## 7. Estado (signals)

- Local en componente (`signal`, `computed`); de feature en servicios con signals dentro de la feature; transversal solo si aplica a toda la app (implementado en M1: `AuthSession` en `core/auth` es el único estado global; el resto es local o de feature).
- Sin NgRx ni store global: no hay necesidad demostrada; se reevaluará con evidencia.
- `linkedSignal` para estado derivado de fuentes que deben permanecer sincronizadas; `resource()`/`httpResource` se usan para fetching reactivo por parámetro (M2: detalle/disponibilidad; M3: propiedad y unidades) y `linkedSignal` en filtros.
- Cuando el backend **no expone lectura** de un recurso (p. ej. publicaciones del anfitrión en M3), el estado de la feature vive en memoria durante la visita (`state/` provisto por ruta) y la limitación se declara en la UI; nunca se deduce de endpoints que devuelven otra cosa ni se persiste como si fuera verdad de servidor (ver ADR-005).
- **Nivel de estado mínimo (M4)**: las reservas **no usan store**. El estado de una reserva es del servidor y de vida corta; cada página usa su propio `resource()` y recarga tras cada acción (`reload()`), con señales locales para el envío y los avisos. No se hereda el patrón de M2/M3 por defecto: el nivel de estado se elige según el alcance real.
- **Mensajería sin store (M4-B, ADR-007)**: hilos, mensajes y notificaciones se cargan con `resource()` por página; el contador de no leídas se muestra donde se consulta (bandeja de notificaciones) y **no** se promociona a `core` ni se pinta en el shell (`layout` no debe depender de una feature y no hay necesidad real de sincronizarlo). Frescura **bajo demanda**: carga inicial, botón «Actualizar» y `reload()` tras cada acción — sin polling, SSE ni WebSockets.

- **Nivel de estado mínimo (M5)**: comunidad y reputación **tampoco usan store**. Actividades, resumen y reputación se leen con `resource()` por página y se recargan tras cada mutación (`reload()`); los formularios y los avisos viven en señales locales del componente. La única proyección de lectura permitida (`residentCandidates`, ADR-006) es una **función pura** dentro de la feature, no estado compartido.
- **Una lectura por visita (M5)**: como `GET /users/{id}/reputation` guarda una instantánea en cada lectura, la página de reputación **no** usa `effect`, polling ni recargas reactivas: lee al entrar (o al cambiar de usuario) y solo vuelve a pedir con «Recalcular».
- **Nivel de estado mínimo (M6)**: el área interna **tampoco usa store**. Cada superficie de administración lee con `resource()` por página y recarga tras cada mutación; los **filtros operativos** (cola de casos, estado de documentos/publicaciones, categoría e inactivas de catálogos) viven en los **query params** porque son compartibles y sobreviven a la recarga; el resto del estado (formulario en curso, confirmación de desactivación, avisos) son señales locales. `core` no crece y `shared/ui` solo se reutiliza (no se promociona nada nuevo).
- **Acciones destructivas o de alto impacto (M6)**: desactivar una entrada de catálogo o una regla de beneficio exige **confirmación explícita en dos pasos**; las decisiones de moderación exigen motivo escrito (validado en cliente y en servidor). Un conflicto de estado (409) o un 500 inesperado se muestran explicados, sin simular éxito; desde F0 los 500 no traen detalle interno, así que la UI usa su mensaje genérico.

## 8. Formularios

- Signal Forms (`@angular/forms/signals`) para formularios nuevos: esquema con validadores (`required`, `email`, `minLength`…) y errores accesibles.
- **Validado en M1** (build, tests y E2E real): modelo con `signal()`, `<form [formRoot]>`, `[formField]` en controles nativos (input/select/checkbox) y envío mediante `submission.action` de `form()`. Helper `shared/ui/field-errors.ts` (`firstFieldError`) muestra el primer mensaje tras `touched`; los `fieldErrors` del backend se pintan en el mismo slot. Mensajes de validación en español definidos en el esquema.
- Alternativa: Reactive Forms si surge fricción real; nunca template-driven.
- Las reglas del contrato backend se reflejan (p. ej. contraseña 8–72 en registro/reset), pero **la validación autoritativa es del backend**: mapear `fieldErrors` a los campos.
- Estados: loading, disabled durante envío, error general + errores por campo, mensajes en español.

## 10. Renderizado / SSR (decisión abierta)

- El scaffold incluye SSR (`outputMode: server`, prerender por defecto en `app.routes.server.ts`). **No se decidió** ni SSG ni retirarlo: el SRS no exige SEO (verificado) y no hay despliegue de producción definido.
- Regla vigente: **cada ruta nueva declara su `RenderMode` con justificación**; no heredar `'**': Prerender` sin evaluación. Criterios: contenido público indexable/estático → Prerender/Server; rutas autenticadas o dependientes de sesión en navegador → Client.
- **M1 aplicado**: todas las rutas de sesión (acceso, perfil, verificación, rol) son `RenderMode.Client`, con la justificación escrita en `app.routes.server.ts` (sin valor SEO y dependientes de `localStorage`).
- **M2 aplicado (ADR-004)**: `/` (landing) es `Prerender` (HTML estático generado en build — verificado: `Prerendered 1 static route`); `alojamientos`, `alojamientos/:id`, `favoritos` y el resto quedan `Client` (el descubrimiento exige sesión y no aporta SEO).
- **M3 aplicado**: `/anfitrion`, `/anfitrion/propiedades/:id` y `/anfitrion/propiedades/:id/unidades/:id` son `Client`, con la justificación escrita en `app.routes.server.ts` (área autenticada con rol activo y estado en `localStorage`; sin valor SEO).
- Si el SSR deja de tener un caso de uso real, se evaluará retirarlo (ADR en ese momento). Si el SSR debe hacer fetch de API en servidor, se adelantará `/api` al backend en `server.ts`.

## 12. Seguridad

Notas de M3 sobre contratos reales:

- **`PATCH` de reemplazo también en host**: `PATCH /host/properties/{id}` y `PATCH /host/units/{id}` sobrescriben los campos enviados, así que los formularios envían el recurso completo leído de la API (conservan `cityId` de la propiedad y, en unidades, `typeCode`/`accessibilityCodes`).
- **Publicaciones del anfitrión sin lectura**: no existe `GET /host/publications` (verificado en `HostAccommodationController`) → el estado vive en memoria durante la visita (`HostPublicationsStore`, provisto por las rutas de `/anfitrion`) y la UI declara la limitación; `CONFLICT` al crear se interpreta como "esta unidad ya tiene publicación" (ADR-005).
- **Catálogo, todavía sin endpoint público**: `PUT /host/publications/{id}/catalog-references` existe y no se usa en UI; el alta de publicación envía `services: []` y `applicableRuleCodes: []` (no hay catálogo que alimentarlos sin inventar códigos).
- **Bloqueos**: `[from, to)` — el día `to` no se bloquea (verificado en E2E: bloqueo 08→11 ⇒ 8, 9 y 10 "No disponible"); `DELETE` libera solo bloqueos del anfitrión, nunca reservas.

Notas de M4 (Fase A) sobre contratos reales:

- **Precio obligatorio para reservar**: `UnitBookingQueryService.getUnitBookingInfo` devuelve `null` si falta la publicación **o el precio**; en ese caso crear una reserva responde `404` con el mensaje "Unit not found or without publication" (no distingue cuál falta). La UI lo explica tal cual y evita el envío cuando el detalle no trae `pricing`.
- **Validaciones exactas de creación**: fechas futuras (`@Future`, hoy tampoco vale), `to > from`, ≤366 noches, `occupants > 0` y ≤ capacidad de la unidad, publicación `PUBLICADA` (RN-03) y huésped con verificación `COMPLETO`. Los mínimos/máximos de estancia declarados por el anfitrión **no** se aplican al crear la solicitud: la UI los muestra como información y no bloquea el envío por ellos.
- **Disponibilidad y concurrencia**: el rango se comprueba como lectura en la creación y se bloquea de forma atómica en `accept` (`SELECT … FOR UPDATE` en orden ascendente, `booking.hold-hours=24`); si un día se ocupó entretanto, `accept` responde `409` y la UI recarga el estado real. La confirmación dentro del hold pasa el día a `OCUPADO`; cancelar lo libera.
- **403 doble**: el mismo código cubre "no tienes rol de huésped activo" (guard del controlador) y "verificación insuficiente" (gate del caso de uso) → mensaje de UI con ambas causas y enlace a la verificación, conservando el texto original del servidor.
- **Expiración**: el barrido programado del backend falla por auto-invocación (`sweep → expireStale` sin proxy) y la expiración del camino `confirm` se revierte con la transacción; ver §15 para el detalle y el impacto.

Notas de M4 (Fase B) sobre contratos reales:

- **Crear hilo**: `POST /conversations` quedó corregido en F0 (ya no da 500 `HV000030`), pero el flujo se mantiene: el hilo se crea con `POST /reservations/{id}/messages`, que devuelve `MessageView.conversationId`. La página que abre la conversación consulta antes `GET /conversations` para entrar directo si el hilo ya existe.
- **Sin tiempo real**: no hay ningún canal push en el backend; la UI lo declara y ofrece «Actualizar». Verificado en E2E: un mensaje enviado por la contraparte no aparece hasta actualizar.
- **Sin paginación ni lectura por mensaje**: los hilos llegan completos (con `messageCount` y `lastMessageAt` como resumen); el «no leído» existe solo en notificaciones (`unreadCount` + `readAt` + `POST /notifications/{id}/read`, idempotente).
- **Reporte (RF-052, Esencial)**: `POST /conversations/{id}/reports` con motivo obligatorio (1..1000) devuelve `caseId` (caso en moderación); un segundo reporte del mismo usuario sobre la misma conversación responde **409**. En la UI es una acción **independiente** del bloqueo.
- **Bloqueo (RF-052)**: `POST /users/me/blocks` está roto (500: `conversation_id` NOT NULL); el guard de escritura sí existe (`existsBetween` en ambos sentidos ⇒ 403). La UI expone la acción y nombra el defecto; desbloqueo (`DELETE`, 404 si no existe) y listado quedan cubiertos por contrato.
- **RF-053 parcial**: solo existen límites de contenido (cuerpo 1..2000, motivo 1..1000); no hay detección de patrones de spam ni eventos auditables, así que el frontend no los implementa ni los simula.
- **Acceso**: los endpoints de mensajería **no exigen rol**; la UI usa `authGuard` sin `roleGuard` y refleja el **403** del servidor cuando no se es parte (probado con un tercero) y el **404** cuando el recurso no existe.

Notas de M5 sobre contratos reales:

- **Comunidad — alta con comunidad fijada**: `POST /host/community/activities` exige `propertyId`, `scheduledAt` futura, `capacity > 0` y `enabledParticipantIds` con al menos un residente **de esa propiedad** (si no, **400** «Enabled participants must belong to the property's community»). La UI deriva los candidatos de los datos del propio anfitrión (proyección estrecha) y no inventa residentes; el 400 del servidor se muestra tal cual.
- **Comunidad — confirmación y concurrencia**: `ConfirmAttendanceService` toma el cupo con `SELECT … FOR UPDATE` y responde **409** en cuatro casos reales (`The activity is full`, `The activity was cancelled`, `The activity date has already passed`, `Attendance is already confirmed`). Verificado en E2E: 200 al confirmar, 409 al repetir, 409 sobre una actividad cancelada y **403** («Not part of the authorized community of this activity») para un tercero.
- **Comunidad — retirada**: `withdraw` solo exige una participación `CONFIRMADA`; **no** comprueba estado ni fecha de la actividad (200 en cancelada). La UI respeta ese contrato.
- **Comunidad — resumen (RF-062)**: `GET /community/summary?propertyId` con `available=false` **no** autoriza a mostrar contadores; verificado en E2E que el valor cambia de `false` a `true` al aceptar el consentimiento de privacidad desde el perfil (mismo dato, otra feature).
- **Reputación — evaluación (RF-070)**: `relationId` es el id de la reserva, el sujeto lo deriva el backend (contraparte) y la relación debe estar `CONFIRMADA`; categorías obligatorias 1..5 (**400** «Every category must be rated: missing […]») y una sola evaluación por autor y evento (**409** «This relation was already evaluated»). Verificado en E2E con la reserva confirmada de M4-A: creación 201, duplicado 409, tercero no parte 403 (`Only the evaluated user can dispute this evaluation` al disputar).
- **Reputación — score (RF-071)**: la fórmula real v1 pondera `rating` 0.5, `stays` 0.2, `verification` 0.2, `disputes` 0.1 y devuelve `factors[]` con peso, valor normalizado y contribución; verificado en E2E (4,33 con una evaluación de 5 y 1 estancia confirmada; **1,58** cuando la evaluación pasa a `DISPUTADA`, porque deja de contar).
- **Reputación — disputa (RF-072)**: **roto en el backend** (400 en todos los casos, §15). La UI no lo compensa: ofrece la acción y muestra el mensaje real.
- **Reputación — beneficios (RF-073)**: solo lectura en M5; `/api/v1/admin/reputation/benefit-rules` (administración) no se usa.

Notas de M6 sobre contratos reales:

- **Autorización real**: las autoridades se derivan del **rol activo** (`BearerTokenAuthenticationFilter` → `User.activeRoleCodes()`), así que el `roleGuard` del cliente coincide con el gate del servidor. 401 ⇒ `{"message":"Authentication required"}`; 403 ⇒ `{"message":"Insufficient privileges"}` (sin `ErrorResponse`).
- **Caso completo verificado en E2E**: asignar → iniciar revisión → resolver con resolución (y rechazar con motivo en otro caso) deja la cadena `ABIERTO → ASIGNADO → EN_REVISION → RESUELTO/RECHAZADO` con actor, nota y fecha; el caso cerrado deja de ofrecer acciones y `resolutionHours` da el tiempo de atención (1,21 h en la prueba).
- **Documentos**: aprobar (204) sin motivo y rechazar/solicitar corrección con motivo obligatorio (400 si falta) funcionan; un documento resuelto no se puede volver a revisar (el backend responde 500 por `requirePending`, la UI no ofrece la acción).
- **Publicaciones**: la cola por defecto son las `EN_REVISION`; `CORRECCION_SOLICITADA` con nota devolvió la publicación a `BORRADOR` y `APROBADA` (sin nota) la pasó a `PUBLICADA`, comprobado también en la vista `?estado=PUBLICADA`. El ciclo cruzado con M3 (anfitrión reenvía a revisión → admin aprueba) requirió la API del anfitrión porque el área de anfitrión no tiene lectura de publicaciones tras recargar (limitación de M3, ADR-005).
- **Reglas de beneficio (RF-073)**: crear `DESTACADO` con `minScore 1` hizo aparecer el beneficio en la reputación del anfitrión (1,58 ≥ 1) y **desactivarlo lo retiró** al recargar; el score y la concesión son del backend (el frontend solo configura datos).
- **Catálogos**: el listado, la edición y la desactivación responden bien, pero el **alta falla siempre** (400 con `parentId` nulo, 404 con un UUID inexistente): defecto de backend que impide cumplir RF-083 end-to-end. La UI muestra el `fieldErrors` real (`parentId: parentId is required for hierarchical categories`).
- **Descubrimientos**: `GET /admin/roles` devuelve los roles activos, pero la asignación de rol interno no está en el alcance de M6 ⇒ decisión abierta, documentada y **no** implementada.

## 16. Decisiones (ADRs)

- `docs/architecture/ADR-001-integracion-api-proxy.md` — integración sin CORS: base relativa + proxy dev + same-origin en producción.
- `docs/architecture/ADR-002-organizacion-feature-first.md` — estructura feature-first, límites de dependencia y estado con signals.
- `docs/architecture/ADR-003-sesion-localstorage.md` — persistencia del token opaco en `localStorage` con `AuthSession`, interceptor y guards (alternativas evaluadas contra el contrato real de sesión).
- `docs/architecture/ADR-004-politica-renderizado.md` — política de renderizado por ruta: `Prerender` para la landing estática, `Client` para sesión/descubrimiento (evaluación explícita de SEO, coste, despliegue y sesión).
- `docs/architecture/ADR-005-publicaciones-anfitrion-sin-lectura.md` — área de anfitrión sin endpoint de lectura de publicaciones: estado de sesión (`HostPublicationsStore`), limitación visible en UI y `CONFLICT` de creación interpretado como "ya existe".
- `docs/architecture/ADR-006-proyecciones-lectura-entre-contextos.md` — proyecciones de lectura estrechas por feature (`BookingContext`, `HostUnitRef`) para datos de otro contexto sin romper el aislamiento ni reconstruir estado no expuesto.
- `docs/architecture/ADR-007-mensajeria-sin-tiempo-real.md` — mensajería sin tiempo real: frescura bajo demanda, estado mínimo sin store, creación del hilo por el endpoint que funciona y defectos del backend nombrados en la UI.
- **M5 no añade ADR**: las decisiones de comunidad y reputación quedaron cubiertas por las ya existentes (ADR-002 feature-first y ADR-006 proyección de lectura estrecha para derivar residentes; ADR-007 para la frescura bajo demanda y el «sin store», aplicado igual a actividades, resumen y reputación). Se revisa si M6 introduce algo no cubierto.
- **M6 tampoco añade ADR**: el área interna se resolvió con las decisiones vigentes — ADR-002 (feature `admin` propia, sin tocar `core` ni promocionar `shared/ui`), ADR-006 (proyección de lectura propia para `PublicationView`) y ADR-007 (frescura bajo demanda y **sin store**: los filtros operativos viven en la URL). Las particularidades de administración (guard por rol activo, confirmación de acciones destructivas, 500 explicado) son convenciones de UI documentadas aquí, no decisiones estructurales nuevas.
- **Revisión de ADRs en la auditoría post-M6**: los siete siguen vigentes y ninguno contradice el estado actual. ADR-003 se reafirma (sigue siendo el único estado global), ADR-005 se ha re-verificado (el área de anfitrión continúa sin lectura de publicaciones, deuda #9), ADR-006/007 cubren las proyecciones y el «sin store» de M5/M6 y ADR-004 cubre la política de render (la landing sigue siendo la única ruta prerenderizada). **No se crea ningún ADR nuevo**: la auditoría no introdujo decisiones arquitectónicas, solo correcciones de calidad y la convención de UI del presupuesto mensual (documentada en §5 y en `.clinerules/40`).

## 17. Roadmap (provisional) y definición de terminado

- **M1 (completado y validado)**: Auth + perfil end-to-end.
- **M2 (completado y validado)**: landing con paridad visual (prerenderizada) + búsqueda + detalle + disponibilidad + favoritos.
- **M3 (completado y validado)**: área de anfitrión — propiedades y unidades (alta y edición), publicación 1:1 con transiciones, precio, reglas y bloqueos de disponibilidad.
- **M4 (completado y validado)**: **Fase A (reservas)** — solicitud del huésped, bandeja del anfitrión con decisiones, hold provisional, confirmación, cancelación y expiración; **Fase B (mensajería)** — hilos por reserva, mensajes ordenados, notificaciones con marca de lectura y reporte de conversación.
- **M5 (completado y validado)**: **comunidad** — actividades del anfitrión (alta con comunidad autorizada, listado, detalle con participantes, cancelación) y participación del residente (listado, confirmación, retirada) + resumen agregado con gate de consentimiento; **reputación** — evaluación por estancia confirmada con cinco categorías, score con factores y versión de fórmula, evaluaciones escritas/recibidas, disputa (bloqueada por defecto de backend) y beneficios en solo lectura.
- **M6 (completado y validado)**: **administración** — cola de casos con filtros en URL, trazabilidad y acciones de asignación/revisión/resolución/rechazo (RF-082); indicadores reales de la cola (RF-084, alcance parcial); revisión de documentos de verificación con motivo obligatorio (RF-080); moderación de publicaciones (RF-081); catálogos con jerarquía y desactivación (RF-083, alta bloqueada por el backend) y reglas de beneficio por puntuación mínima (RF-073). RF-085 queda sin contrato de auditoría (solo la trazabilidad de cada caso).
- **M7 (no definido)**: no hay siguiente milestone acordado; M6 se detiene aquí.
- Definición de terminado de una funcionalidad: requisito identificado + contrato backend verificado + TypeScript estricto + build + tests relevantes + estados loading/error/empty + accesibilidad + responsive + seguridad + consistencia visual + memoria/guía actualizadas cuando corresponda.
